## 已确认问题

### F1 · P1：恢复备份没有拦截排队中的社媒任务

复现步骤：

1. 在临时库创建企业并备份。
2. 给该企业创建社媒发现任务，保持 `queued`。
3. 调用 `/api/backups/restore` 恢复此前备份。

实际返回 HTTP 200，随后 `/api/social/runs` 返回空列表。界面文字要求活动任务先停止，但后端只检查普通任务 `active_runs()`，没有检查社媒任务。操作锁能保护正在持锁的处理过程，不能替代队列状态检查。

影响：用户可能在未明确取消社媒任务时，通过恢复备份丢失排队任务及恢复点之后的进度。

建议：恢复前统一检查普通任务和社媒任务，并在同一并发控制范围内完成检查与恢复。补充 queued、running、取消后恢复三类回归。

位置：`leadworkbench/api.py` 的 `/api/backups/restore`。

### F2 · P2：无官网企业无法人工录入，且错误提示不可读

界面操作：人工录入企业，只填写名称，官网留空，点击保存。

实际：界面允许提交，但 API 返回 422，并直接展示包含 `string_too_short`、`loc`、`min_length` 的英文 JSON。填写有效官网后保存成功。

影响：没有官网的目标企业无法从这个入口保存；用户不知道如何修正。

建议：允许官网为空，按字段展示中文错误；后续官网补全任务按是否存在网址处理。若业务坚持必填，也必须同步前端必填说明，但这不符合当前“尽可能收录市场企业”的目标。

位置：`leadworkbench/api.py` 的 `CompanyInput`；`frontend/src/forms.tsx` 的企业录入表单。

### F3 · P2：变化历史仍显示原始 JSON

实际浏览器可见：

- 业务类型从 `[]` 变为 `["wholesaler"]`。
- 联系人识别修正记录直接展示含 `id`、`company_id`、`fingerprint` 等字段的整段 JSON。

影响：审核卡片已改善，但详情页和更新记录仍难阅读，内部编码淹没姓名、岗位、邮箱等信息。

建议：使用统一字段展示组件：业务类型翻译为中文标签；联系人变化显示姓名、邮箱、岗位、采用状态；原始结构仅放在可选的原始证据折叠区域。

### F4 · P2：设置页定时计划仅显示目标内部 ID

创建企业复核计划后，设置页显示 `目标：df664b…`，没有企业名称。

影响：计划较多时，无法判断每条计划服务于哪家企业或哪个市场。

建议：展示企业/市场名称、地区和可点击详情入口，ID 不作为主展示值。

## 验收边界与建议顺序

1. 先修 F1，避免恢复备份与异步社媒任务状态不一致。
2. 修 F2，让无官网企业也可进入企业库，并改善错误提示。
3. 合并修 F3/F4，统一用户可读的数据展示。
4. 单独处理 SearxNG 上游连接和平台公开页面超时，再补跑真实社媒成功链路。

本次不是城市级穷尽采集验收、所有社交平台的兼容性认证或长期稳定性测试。没有登录平台，没有测试外发邮件/评论（产品当前只保存草稿与人工跟进记录）。浏览器逐项验证主要路径，较多边界和并发场景由自动化测试覆盖；移动端、其他浏览器及大规模长期运行未在本次验证。
