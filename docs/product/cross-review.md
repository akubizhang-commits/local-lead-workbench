# PRD、交互与UI交叉评审

版本：1.0｜2026-09-23  
评审对象：[PRD](overseas-lead-acquisition.prd.md)、[交互设计](interaction-design.md)、[UI设计](ui-design.md)，以及当前代码与部分页面。

2026-09-25 维护说明：原评审发现保留历史上下文；PRD-04/IX-02/UI-04 已同步市场社媒并行补全。三通道、平台独立等待、未来设置/执行快照、历史显式补充的最终验收见[实施审计](../validation/2026-09-25-market-social-integration.md)，不以本文原有测试计数代替本轮集成结果。

## 1. 结论

项目已有早期PRD，但它没有跟上目标与实现。当前系统能够支持企业发现、资料整理、候选核验和部分跟进记账；**还不是完成“找到关键人员 → 向指定入口发送 → 跟进回复”的获客闭环产品。**

新版文档把这条完整业务线纳入目标，同时保留当前实现边界。建议先补齐“联系对象与入口”和“草稿/触达”之间的断点，再逐个接入实际发送通道；不能通过改一个按钮名称就把人工记账当作发送能力。

本轮只整理文档、核对实现和提出整改项。下文“已纳入文档”不表示代码已经修复。

## 2. 评审方法与证据

- 产品/后端视角：核对市场检索、去重、官网和社媒识别、导出、发送及跟进，见[只读能力核对](../audits/2026-09-23/产品后端能力只读核对.md)。
- 前端/交互视角：核对页面入口、对象选择、状态反馈、草稿生命周期与CSS。
- 交叉核对：以PRD编号逐条查找交互入口、UI呈现和验收场景；检查是否把规划功能写成已有。
- 页面体验：本轮只读查看企业库，观察到筛选、说明、导出和批量区占首屏较多空间；其他页面依据源码及前轮页面验证，不冒充本轮全量实测。
- CSS对比度是静态计算，草稿丢失与地区联动风险为代码路径发现，尚未在本轮用真实业务记录复现。
- 本轮没有重新执行完整测试、真实城市召回实验、人员准确率评估或实际发信。

代码位置均相对项目根目录 `<项目目录>`；行号对应本次评审版本。

## 3. 主要发现

### R01｜P1｜实际发送与回复闭环缺失【新增目标差距】

用户目标包括向指定入口发送产品介绍。当前`api.py:422`调用的只是`social_store.py:106`记录方法；`SocialFollowup.tsx:30`的目标也只包含已确认社媒账号/帖子。没有邮件发送、社媒发送回执和统一回复链路。

后果：采集后仍要自行组织收件入口、发送和追踪；采购邮箱甚至不能进入现有社媒草稿工作流。

文档处理：PRD-08～10、IX-06～08、UI-04/06明确新增能力；邮件与各社媒通道独立验收。格式待定不阻塞定义收件对象、草稿和结果语义。

代码状态：**未实现，不能对外宣称已有。**

### R02｜P1｜企业账号归属和采购/关键人员身份没有连通【部分实现】

`sources/social_profile.py:9`主要提供域名和电话匹配信号；`social_store.py:89`允许选择员工等范围，但不等于绑定具体人员及其岗位。`SocialEntry.tsx:98`的归属确认与`SocialAccountSummary.tsx:73`显示的字段仍是两件事。

后果：企业账号数量增加，并不代表采购联系人增加；选择“员工”可能被误读为找到决策人。

文档处理：PRD-05/06、IX-05、UI-05分别约束企业归属、岗位证据和联系方式对应；新增“关联到联系人”，保留品牌/门店入口。

代码状态：**需要完善。**

### R03｜P1｜“指定城市所有相关企业”缺少地域和覆盖验收【部分实现】

`market_plan.py:259`生成近似范围与网格；`market_worker.py:5`有内部任务预算；`market_store.py:497`展示计划检索进度。新建企业在`market_store.py:343`使用任务城市标签，并不能证明实际地址属于该行政区。

后果：用户可能把检索完成度当成企业覆盖率，或把邻近城市结果当成指定城市企业。

文档处理：PRD-02/03和IX-02要求分开目标市场与实际地域，保留范围外/无法定位结果；展示尚未完成部分，不要求用户设置名单上限。UI-06明确“本轮检索结束”文案。

代码状态：**近似检索可用，地域核验与真实漏检评估仍待完善。**

### R04｜P1｜草稿跨页面保存存在断点【代码路径发现，待专项复现】

`CompanyDetailPage.tsx:40`和`:130`在不同分支位置挂载SocialPanel；草稿存于`social/useFollowupDraft.ts:3`的组件内部状态。面板级测试并不能证明完整App路由切换后还保留草稿。

后果：从企业详情切换账号详情或返回时可能丢失未保存内容；对未来邮件编辑尤其不适合。

文档处理：IX-06、IT08要求草稿按目标保存，已保存的内容可恢复；未保存离开要有提示。

代码状态：**需补真实页面层回归和修复，不能继续承诺所有页面切换均不丢草稿。**

### R05｜P1（发送前）/P2（当前）｜切换目标沿用旧正文【代码路径发现】

`SocialFollowup.tsx:59`切换目标时只改目标与确认状态；`useFollowupDraft.ts:9`也保留正文。

后果：当前可能把A的内容错记到B；未来接入发送后会变成发错内容的风险。没有证据表明现在已经误发送，因为尚无发送功能。

文档处理：IX-06/07规定目标独立草稿，复制内容必须显式进行；IT07/10验证。

代码状态：**应在实际发送前解决。**

### R06｜P2｜地区联动可能提交混合地域【代码路径发现】

`frontend/src/forms.tsx:10`修改国家/州的状态没有同步清空所有下级文本输入，而提交读取FormData。

后果：可能将新国家和旧州/城市一起提交，影响全流程搜索。

文档处理：IX-02与IT01明确清理/核对下级值及自定义地区提示。

代码状态：**待修复并验证。**

### R07｜P2｜联系入口筛选、统计与导出未完全服务于触达【部分实现】

企业库已有采购、其他社媒、其他邮箱数量，但入口筛选当前只有采购和其他邮箱；CSV仍是企业表，`export.py:28`无联系人邮箱列，XLSX没有完整的社媒目标和跟进结构。`contactList.ts:4`与后端统计各有分类逻辑。

后果：用户知道有社媒入口，却不一定能筛出、导出或使用同一口径的对象清单；人员和入口数也容易混淆。

文档处理：PRD-06/11定义不重叠、单位明确的统计与入口级导出；IX-03明确筛选和导出的范围。不能仅换导出按钮标题。

代码状态：**需统一入口口径与触达数据交付。**

### R08｜P2｜状态维度多，容易出现“已验证”的误读【设计治理】

任务完成、符合目标客户、账号归属确认、岗位证据明确、人工记录已联系分别属于不同维度。

后果：阅读成本高，也可能让普通公开账号看起来像已验证采购人，或把人工补记当投递证明。

文档处理：PRD第4节、IX-09、UI-06建立统一术语；发送状态单独定义。

代码状态：**已有部分区分，仍需统一文案与状态组件。**

### R09｜P2｜低对比小文字与首屏密度影响判断【视觉发现】

`styles.css:1`中次要文字对白底约3.78:1，部分提示约2.64:1；状态、解释与证据常用10～12px。企业库截图还显示常驻说明和工具区占据较多首屏。

后果：真正需要判断的企业、岗位、来源和下一步不够突出。

文档处理：UI-02/03建议压缩说明区、增加正文与辅助字可读性，并按VT01/02/05/06验收。CSS计算不等于完成无障碍认证。

代码状态：**本轮未改视觉，待实施。**

### R10｜P2｜旧文档与现状冲突【本轮文档修正】

旧requirements仍有“尚未实现”“最多100家”和“不做发送”；旧技术稿也不是当前实际架构。若继续直接按旧稿验收，会把用户新目标排除。

文档处理：增加新版入口，保留旧稿并标为历史参考；新文档明确已实现、部分实现、未实现、建议和待定。

状态：**本轮已处理文档入口和范围声明；旧历史文本不作为现行验收标准。**

## 5. 整改顺序建议

### 第一批：让线索成为可使用的联系对象

- 定义首轮销售产品、目标客户和关键岗位（Q01）。
- 统一企业、具体人员、部门及账号的关系和不重叠口径（R02、R07、R08）。
- 补地域归属与范围未完成提示，修地区联动（R03、R06）。
- 采购邮箱和社媒均能进入统一“准备联系”，草稿按对象保存（R01、R04、R05）。

### 第二批：完成一次真实触达闭环

- 明确发件身份和首个发送通道（Q02、Q03）。
- 以受控收件对象验证预览、确认、发送、结果、重复保护。
- 再逐个平台开放，明确“可读取”和“可发送”的区别。
- 接入统一跟进；自动结果和人工补记分开。

### 第三批：提高日常使用效率

- 调整列表密度、文字对比和辅助信息层级（R09）。
- 完善入口级筛选、导出、批量操作和效果指标。
- 根据实际规模再决定团队协作、批量触达和更多市场支持。

没有估算开发工期：发送方式、产品输入与平台可行性仍未确定，给出固定日期会失真。

## 6. 评审放行条件

文档可以作为下一轮讨论与任务拆解基线，但不应直接据此宣布完整产品验收通过。

- 定义首轮销售产品、目标岗位与消息内容最小字段。
- 明确首个发送通道及真实结果的凭据。
- 对R03～R07的实际代码风险补针对性测试，尤其是完整路由草稿保留和跨对象内容隔离。
- 以相同联系对象贯穿发现、核对、准备、发送、回复，不在每个阶段重新手工拼接。
- 分开报告：代码存在、自动测试通过、真实来源可读、身份准确、真实发送成功和业务对话结果。

平台可访问性、数据使用和具体发送约束没有在本轮做外部验证，仍是实施/上线依赖；这里不作法律结论或平台能力保证。

## 7. 文档交叉核对后的修订

第一轮独立核对并非直接通过：产品/后端和交互/UI分别指出了口径与状态转换的缺口。本稿据此进行了以下修订。这里关闭的是文档歧义，前述代码整改项仍按其原状态保留。

| 交叉核对问题 | 修订位置 | 处理结果 |
|---|---|---|
| 采购与关键员工重叠、多人/门店共用入口如何计数 | PRD-06、IX-04、UI-05 | 明确采购优先、人员不强并、共享入口计一次、待确认与可用分开；补四个例子 |
| 切换目标加载另一草稿可能绕过未保存保护 | IX-06、IT07 | 必须先保存成功或明确放弃；取消/保存失败留在原对象 |
| “关联到联系人”缺少可操作入口与反馈 | IX-05、UI-04/06 | 增加身份与归属区的入口、采用依据、成功/失败状态 |
| 待确认、不采用和冲突入口能否发送未定义 | PRD-09、IX-07 | 增准入表，预览及提交时复查；普通业务入口不要求采购身份 |
| 受理后退信、结果未知的核对路径不完整 | PRD-09、IX-07、UI-06 | 增后续投递失败，保留原凭据；明确自动/人工核对及解除重发限制条件 |
| 策略耗尽与可重试失败共用“继续” | PRD-02、IX-02/09 | 分开“重试未完成项”和“查看限制/调整策略”，不保证新一轮扩大覆盖 |
| 产品链接既被列为最小能力又被写成待定 | PRD-08、UI-04 | 正文普通文本链接可用；结构化链接、附件、签名和变量待定 |

最终追踪检查覆盖11项PRD需求，每项均关联交互、UI或验收规则；文档相对链接已检查。业务输入与实际通道可行性未因此被视为已确定。
