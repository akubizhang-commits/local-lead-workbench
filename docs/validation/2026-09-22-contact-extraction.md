# 联系人字段识别修复验收

## 目标与边界

企业员工、采购部门、公开联系渠道分别处理。服务卡片、文章标题和导航文案不能因为出现 buyer / sourcing 就成为采购人员。每个已提取字段必须能追溯到原始页面，不猜测姓名、邮箱或雇佣关系。

实现采用本地确定性规则，不引入收费服务或模型依赖。JSON-LD 和 Microdata Person 需要明确匹配本站企业的 worksFor 证据，排除文章作者。对普通 HTML 保留人员卡片结构，限制字段归属范围，不跨相邻卡片拼接；岗位按完整短语识别。

重复来源汇总为一张卡片，原始来源记录不删除；有冲突的字段保留独立值及来源。采购人员与采购部门分别展示，销售等其他联系人默认收起。

## 实际官网样本

2026-09-22 读取公开页面快照，仅在临时目录进行解析，不把测试结果写入真实数据库。

- Fashion Atlas Group wholesale-clothing 页面：282024 字节。原先 Quality Control / Buyer protection 等误识别不再产生联系人。结果为 0 名人员、3 条联系渠道（两个公开邮箱写法和一个联系页面）。
- 页面本身存在显示邮箱 .com 与 mailto 链接 .co 的差异。保留两条来源事实，不自动认定或合成“正确邮箱”，也不声称已验证收信能力。
- 试点企业A sales-reps 页面：462870 字节。识别出 7 名员工及 1 条企业渠道。其中 2 名 Buyer 归入采购人员；联系人 C 的邮箱、销售经理岗位、电话、分机、WhatsApp、语言与页面对应。Sales Rep 缩写纳入合法岗位测试。

临时快照及解析结果：`/tmp/contact-quality-verification/`。快照不作为仓库中的长期测试数据。

最终定向回归：109 项测试通过，44 个子测试通过；上述两个真实页面快照的结果断言全部通过。

## 回归覆盖

- 截图中的服务标题、营销句、文章标题、跨卡片误关联。
- 正常人员姓名、Sales Rep、采购岗位、无邮箱但有明确岗位人员。
- 通用邮箱不能绑定为个人邮箱；采购部门不冒充具名人员。
- JSON-LD/Microdata 的本站雇佣关系、作者排除及资源边界。
- 多页面重复记录汇总，多来源证据保留；错误归属修复仍保留真实公开邮箱。
- 历史错误记录归档与变更日志，重复执行不重复归档。

## 旧数据升级

`scripts/reclassify_contacts.py` 默认只预览。加 `--apply` 时先用 SQLite backup API 保存一致性快照，再归档确定误识别的记录。被误绑定的公开邮箱若原文中明确存在，则保留为企业渠道。原始记录与证据留在数据库，处理原因记录在更新历史。

应用重启与真实库升级已由并行“爬虫”审计修复任务统一执行。2026-09-22 15:49 在正式本地页面验收：后台采集在线，Fashion Atlas 显示 3 个公开联系渠道、0 个采购联系人；展开其他联系人可见两个邮箱和联系页面，各字段带来源入口。原误识别记录在更新历史中保留。
