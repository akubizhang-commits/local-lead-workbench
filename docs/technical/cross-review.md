# 技术文档交叉评审与实施追踪

版本 1.0 · 2026-09-23

2026-09-25 同步：本文原评审发现保留日期与上下文；当前三通道、市场社媒父子轮次、平台门控及最终验证状态见[集成设计](market-social-integration.md)和[实施审计](../validation/2026-09-25-market-social-integration.md)。本次文档维护未重新开展独立代码评审。

## 1. 评审范围与结论

评审对象为本目录架构、拓扑、模块、API、数据库与规划触达设计，并对照新版 PRD、交互、UI 文档及当前源码。目标是建立可用于后续开发的技术基线，不能将文档完成解释为发送功能或架构整改已实现。

当前结构适合继续本机内部测试：API 与 Worker 分进程，共用 SQLite，来源适配与业务投影已分文件；尚不具备多租户服务部署条件。核心产品缺口仍是人员身份到联系入口、持久草稿到真实发送与回复之间的闭环。

## 2. 交叉评审方法

| 评审角色 | 编写 / 核对范围 | 交叉检查 |
|---|---|---|
| 主评审 | 整体架构、拓扑、规划触达、技术索引 | 对照模块内部调用、产品状态语义；核对接口与DDL附件及文档链接 |
| 后端/数据评审 | API、数据库、离线附件 | 从模块图查真实方法、响应和表关系，区分声明FK与逻辑引用 |
| 模块/交互评审 | 五个模块与时序、前端数据流 | 对照API/DB与整体架构，检查草稿和发送目标设计是否遗漏交互要求 |
| 独立架构评审 | 不参与上述初稿编写 | 对照代码复查进程/共享状态与规划发送的并发、幂等、身份边界 |

评审使用独立任务进行，不把同一稿件改写一遍称为交叉评审。临时协议检查与DDL重放采用隔离目录/内存库，未向实际平台发送请求或消息。

## 3. 已发现并纠正的文档问题

| 编号 | 发现 | 处理 | 代码状态 |
|---|---|---|---|
| D01 | 规划草稿只列正文，遗漏交互要求中的邮件主题 | subject加入草稿、API、预览和发送内容快照；非邮件主题为空 | 规划补齐，未实现 |
| D02 | 规划发送时序只在提交时校验，遗漏排队后新增拒绝联系与取消竞争 | 执行器出站前重查；条件更新裁决领取/取消；准入失效不出站；裁决后不承诺撤回 | 规划补齐，未实现 |
| D03 | 原技术建议仍可能被误认当前架构和接口 | 新技术索引关联代码快照；旧接口文档加入历史标记；明确不使用SQLAlchemy/Alembic | 仅文档更新 |
| D04 | 新建库与完整运行schema表数不同 | 说明30张启动表与1张按需耗尽表；DDL包含按需表及注释 | 当前实现未改 |
| D05 | OpenAPI成功响应schema为空，不能作为完整契约 | 明确附件限制；人工补充响应、错误、认证、幂等及文件导出语义 | 当前实现未改 |
| D06 | 请求幂等无法覆盖不同门店/不同请求键重复发送共享账号 | 跨company的business_dedupe_key活动占用；Unknown不释放；撤下尚无batch模型的批次保证 | 规划补齐，未实现 |
| D07 | 崩溃进程不可能自行写Unknown，恢复协议缺失 | 新增send_attempt、独立Recovery泳道、确认旧进程退出、版本条件更新；不以租约到期等同停止 | 规划补齐，未实现 |
| D08 | 发件账号换绑可能改变用户已确认的发送身份 | sender_revision及身份快照绑定preview和命令；换绑使旧预览/排队命令失效 | 规划补齐，未实现 |
| D09 | 私信与帖子回复没有明确动作及回复目标 | action/reply_target入草稿、预览、摘要与内容快照；不支持动作不开放 | 规划补齐，未实现 |
| D10 | 架构和拓扑遗漏城市定位外部服务 | 加入默认Nominatim/可配置端点、独立调用及缓存说明 | 当前实现未改 |
| D11 | 登录时序画成Worker直接回传API | 改成Worker写SQLite，界面经API轮询数据库 | 当前实现未改 |
| D12 | 模块内部接口把_outcome/_changed写成必返 | 标为可选，说明较旧来源提前返回路径 | 当前实现未改 |
| D13 | 模块将reader=browser误写默认配置 | 改为显式配置；默认reader实际为HTTP | 当前实现未改 |

D01/D02由模块/交互独立评审提出；D03～D05为源码核对时的文档治理问题；独立架构评审补充D02的竞争语义及D06～D11；后端/数据互审提出D12/D13。

最终复核：独立架构评审对其7项发现逐项确认关闭；模块/交互评审确认主题及出站准入两项已补齐；后端/模块互审确认可选返回字段与默认HTTP两项已修正。关闭的是文档与规划设计问题，§5中的实施缺口仍保留。

## 5. 后续代码整改建议（本轮未实施）

| 优先级 | 问题 | 建议下一步与可验证出口 |
|---|---|---|
| P1，发送接入前 | 联系人/员工范围尚未形成稳定人员身份；草稿组件卸载与切换目标存在断点 | 先实现目标身份、持久草稿和版本保护，覆盖完整App路由切换/保存失败/共享入口 |
| P1，发送接入前 | 现有人工outreach无请求幂等/实际回执 | 新发送命令与事件模型，不改名复用人工记录；重复提交、超时、退信、拒绝联系专项测试 |
| P1，面向市场覆盖承诺前 | 近似网格、任务城市标签不能证明实际行政地域和全城覆盖 | 独立存实际地域与目标市场；范围外/不确定结果可追溯，做召回样本验证 |
| P2 | API没有业务response_model；TS泛型不做运行时验证 | 先给关键企业/社媒/任务响应定义契约并做前后端一致性测试 |
| P2 | schema版本号2之后还有启动数据修复和按需DDL | 梳理可复现迁移序列，结构变更与历史业务清理分离；旧库fixture升级测试 |
| P2 | API串行化、单Worker三通道内非抢占、平台等待、投影累积历史 | 在稳定优先的单通道并发与节奏下测延迟/队列等待；三通道不等于严格公平或可任意增并发 |
| P2 | 导出、入口筛选和统计口径分散 | 统一入口投影及单位，覆盖候选/排除/共享账号与不同格式导出 |
| P2，外部部署前 | 本地令牌和文件权限不等于租户认证或凭据加密 | 单独设计多人身份、租户隔离、凭据管理与部署；本轮不改回环监听 |

这些是文档评审归纳的实施项，不意味着已经修改了现有代码，也不意味着本轮重新发现或复现了此前所有产品问题。

## 6. 验证范围

- API/DB评审在临时Store及进程内ASGI中核对协议示例、部分错误/revision/排队响应；不启动worker，不访问外部来源。
- 完整DDL在内存SQLite重放，通过结构完整性和外键检查。空库外键检查不能证明真实历史数据都无孤儿关联。
- 主评审检查生成附件与源码指纹、路由集合、相对文档链接、图清单与ER表名，结果保存在 `validation.json`。
- Mermaid图保留可编辑源码；本轮的图检查是结构/引用检查，不冒充逐图视觉渲染验收。
- 本轮没有修改业务实现、重启服务、运行实际采集、恢复真实数据库或发送消息；没有重新运行完整后端/前端回归、真实平台测试及性能压测。

## 7. 文档检查复现

在项目根目录运行：

```bash
python3 docs/technical/validate_docs.py
```

该脚本只读取源码和文档，在内存重放 DDL，写回本目录 source-manifest.json 与 validation.json；当前计数以该结果为准，包含源码指纹、业务 API 与 SPA 路由、完整结构表、索引和图清单。脚本内 documentation_date 仍固定为历史日期 2026-09-24，本次实际检查日期另记于实施审计；不把这个历史标签当作执行时间。OpenAPI/schema 再生成方法分别见 API 与数据库文档。
