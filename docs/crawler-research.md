# 免费本地爬虫方案调研

调研日期：2026-09-22  
状态：官方文档与开源仓库调研；未安装候选爬虫，未执行 Maps 抓取或性能测试  
关联：[需求文档](./requirements.md) · [技术设计](./technical-design.md)

## 1. 推荐结论

采用“两阶段选择、两类爬虫”：

1. **Maps 发现先验证现成开源项目**：将 `gosom/google-maps-scraper` 作为 M0 首选候选，评估当前机器及网络能否正常运行，并满足出处记录与停止控制。
2. **保留自建 Playwright 路线**：如果现成项目难以提供字段出处、错误分类或可控暂停，就采用原技术设计的 Playwright 适配器；不同时开发两套完整采集器。
3. **官网补全使用 HTTPX＋HTML 解析＋按需 Playwright**：静态页面不启动浏览器，不要求 AI。
4. **采购人员匹配单独实现**：普通邮箱抓取不能替代岗位与邮箱归属证据。
5. **不引入付费运行依赖**：Maps API、搜索 API、托管采集、联系人数据库、邮箱校验、付费代理和在线模型均不作为本版运行条件。

这是基于文档能力与产品需求的工程建议，不是实测胜负结论。免费本地软件仍有设备、现有网络、电力及人工维护成本。当前网络无法访问 Maps 时记录阻塞，不以新增付费服务补救。

## 2. 调研方法与证据边界

本轮读取维护方仓库 README、许可证及官方技术文档；资料索引在文末。

- **文档确认**：维护方明确列出的功能或限制。
- **设计判断**：根据本项目作出的选型与接口建议。
- **尚未验证**：本机安装、现有网络成功率、资源占用、字段准确率和长期可用性。

没有将 README 的性能宣传当作本机性能，没有将软件许可证当作目标网站数据许可，也不将免费试用额度作为可持续的免费方案。

## 3. 候选比较

| 方案 | 文档确认的能力 | 我们仍需实现 | 本项目判断 |
|---|---|---|---|
| gosom/google-maps-scraper | Maps 专用、本地 CLI/Web UI/REST、导出、网格、文件续跑 [R1] | 业务去重、证据映射、更新、采购身份、范围过滤 | **M0 优先验证** |
| Playwright 自建 | 浏览器动作自动等待及可执行性检查 [R3] | Maps 查询、滚动、解析和任务状态 | **可控的产品适配器备选** |
| Selenium 自建 | 浏览器交互和多种等待策略 [R4] | 动态页面状态与来源解析 | 已有团队资产时再选 |
| Crawlee Python | 持久化请求队列、数据集及本地文件存储 [R5] | Maps 解析、企业与联系人模型 | 框架备选，不立即替换业务队列 |
| Scrapy | 请求队列、去重和任务持久化 [R6] | Maps 浏览器交互及业务系统 | 大量静态官网抓取时再评估 |
| Crawl4AI | 无 LLM 的 CSS/XPath/正则提取 [R7] | Maps 操作、采购归属与审核 | 可选内容处理工具 |
| HTTPX＋HTML 解析 | 异步 HTTP、连接复用、流式读取 [R8] | 链接调度、解析和动态页面回退 | **官网静态读取首选** |

不将全部工具叠加到同一条运行链路。主栈保持 Python；独立 Maps 程序可以经子进程适配，不要求整个产品改写语言。

## 4. Maps 首选候选：gosom/google-maps-scraper

### 4.1 已确认能力与限制

仓库采用 MIT 许可证，README 提供本地 CLI、Web UI/REST、CSV/JSON、网格、文件续跑及可选官网邮箱采集。[R1][R2]

需要特别区分：

- `-grid-bbox` 不严格裁剪结果，需要后置地理过滤。
- `-depth` 是滚动深度，不是企业数量。
- `-resume` 跳过已经写出的地点及完成的查询，用于续跑，不是重新核验。
- `-email` 访问企业网站查找邮箱，默认关闭；没有承诺识别采购人员。
- 提供遥测退出变量 `DISABLE_TELEMETRY=1`。
- 文档包含赞助商和云服务推广，不属于本地核心功能的必需依赖。[R1]

本轮没有完成全部代码路径、依赖和网络行为审查，也没有运行程序。不能据此宣称它已经满足既有技术文档的安全、证据和停止策略。

### 4.2 建议验证方式

以下为待执行计划：

1. 锁定版本／commit，在独立测试目录中运行；先评估 macOS 原生部署，容器只作备选。
2. 不自动安装项目附带的 Agent Skill，不执行远程一键部署脚本，不启用托管服务。
3. 关闭遥测，不使用付费代理、代理轮换或 API Key 服务。
4. 显式设置并发 1；关闭邮箱、额外评论等非企业发现能力，隔离问题。
5. 每个查询独立记录配置、程序版本、输出目录、开始结束时间和退出状态。
6. 检查实际输出 schema，验证来源标识、名称、地址、官网、坐标能否映射到业务观察记录。
7. 对字段级来源缺失、无法停止、来源阻塞等情况记录缺口，不根据功能清单推测支持。

输出进入包装适配器，再转为 Observation，不直接覆盖企业表。有结果文件与任务完全成功分开判断，支持“有部分结果但因访问限制中止”。

### 4.3 不交给它默认处理的业务

企业／门店归属、行业分类、官网身份核验、采购邮箱对应、字段历史、人工备注保护和定期复核仍由产品层负责。第三方工具输出变更不应改变这些规则。

### 4.4 采用与放弃条件

- **采用**：在现有网络下取得真实结果，来源可追溯，错误与停止可控，包装或小范围修改即可满足产品契约。
- **转用自建 Playwright**：基本可访问，但解析证据、错误分类、任务控制难以适配，改造成本接近自建。
- **暂停 Maps 路线**：两种实现均被相同网络或来源限制持续阻塞。换库不能被当成解决所有访问限制的方法。

## 5. 自建 Playwright 的技术路线

Playwright 的自动等待检查元素是否可操作，不能自动判定结果列表是否全部加载。[R3] 因此必须显式建模页面状态：

```text
打开查询
  -> 正常结果列表
  -> 明确无结果
  -> 同意页面／需要人工处理
  -> 验证码／登录／访问拒绝
  -> 未识别页面结构
```

正常列表循环：

1. 提取当前可见的来源链接并去重。
2. 打开详情，读取实际字段并记录证据定位。
3. 提交观察事实和检查点。
4. 返回列表并滚动。
5. 根据明确结束提示、连续无新增批次、数量／时间限制决定停止。

第一版保持可见浏览器模式便于诊断，跑通后再比较无头模式。初始路线不依赖复制未公开网络接口请求。

复用产品 SQLite 队列，不把仅存在内存的列表当成恢复机制。用真实页面测试与合成解析夹具分别验证，合成夹具禁止计入真实采集结果。

## 6. Crawlee：本地可用，但先不替换业务队列

官方文档说明 FileSystemStorageClient 能将 Dataset、KeyValueStore 和 RequestQueue 保存到本地。使用这种模式不需要 Apify 云存储。[R5]

具体注意：

- `purge_on_start` 默认 true，恢复场景必须显式配置。
- FileSystemStorageClient 不支持多个爬虫进程并发访问同一存储。
- 当前文档将 SQL 存储客户端标记为实验功能。[R5]

本项目判断：现有业务仍需要 SQLite 保存企业、联系人、审核和计划，现在切换框架不一定减少总复杂度。

如果后续采用：

- Crawlee 仅管理单次 job 的页面队列。
- 每次 run 使用独立命名空间；恢复复用原 run，旧资料复核创建新 run。
- 企业、联系人与人工备注仍由业务库管理。
- 禁用不符合本项目策略的自动换会话／代理行为。
- 避免框架和业务层同时重复重试，或续跑去重使旧页面永远不再复核。

## 7. 官网和采购邮箱

### 7.1 免费组合

HTTPX AsyncClient 复用连接，HTML 解析器提取正文、`mailto:` 及联系／团队页链接；确需 JavaScript 时再启用 Playwright。[R8][R3]

页面顺序按业务规则：Contact、About、Team、Buying、Purchasing、Sourcing、Vendor、Supplier。建议预算沿用技术文档：每企业域名最多 20 页、深度 2。先覆盖英语站点，后续增加当地语言词典。

### 7.2 以页面区块核验归属

- 同一人物卡片内明确对应的姓名、职位和邮箱形成候选关系。
- 采购页面上的部门邮箱计为部门入口，不伪造人员姓名。
- 全站页脚客服邮箱只挂企业，不能分配给页面中所有人员。
- 供应商申请页或联系表单也可成为可操作的采购入口。
- 没有公开信息则返回未找到，不猜邮箱格式。

技术校验与身份核验分开。第一版不调用邮箱验证 API，不通过测试邮件或 SMTP 探测证明邮箱存在。

### 7.3 Crawl4AI 的位置

官方文档提供无需模型的提取方式，所以使用其 CSS/XPath/正则能力不必依赖付费 AI。[R7]

本项目判断：有限的联系人字段先用简单规则处理；如果后续需要大量正文清洗，再单独比较 Crawl4AI。引入时检查选定版本的实际 LICENSE/NOTICE，本轮不对未审查的许可证作保证。

规则提取也会出错，不能因为“不用 LLM”就免除归属审核。

## 8. 社交媒体的免费实现范围

不购买联系人数据库或社交媒体采集服务，也不依赖试用额度：

1. 从企业官网提取关联的官方账号。
2. 对可使用的公开页面提取有来源的工作信息。
3. 无法自动取得的页面展示人工核验入口。
4. 人工补充明确标记录入方式。

LinkedIn 用户协议限制未经授权的自动抓取；本版不将批量自动获取 LinkedIn 采购人员写成必达能力。[R9] 其他平台也不自动推定与普通官网具有相同可访问性。

实际目标是测出公开采购入口发现率，而不是为每家企业填满所有字段。

## 9. 不付费的运行约束

| 项目 | 处理 |
|---|---|
| Maps／搜索 API | 不接入，不依赖免费额度 |
| 代理与验证码服务 | 不采购，不设计自动付费兜底 |
| 网络 | 使用现有可用网络；不可达则记录阻塞 |
| 联系人及邮箱验证服务 | 不接入 |
| 在线模型 | 不调用；默认规则提取 |
| 本地模型 | 仅为后续可选实验，按设备和模型许可评估 |
| 存储 | 本地数据库和文件 |
| 安装 | 原生环境优先，不把容器桌面软件当成无条件免费的必需组件 |
| 遥测与推广 | 关闭可关闭的遥测，不使用附带推广服务 |

M0 需检查 CPU 架构、可用内存、磁盘、浏览器启动、DNS/TLS、Maps 连通性及依赖下载条件。没有执行这些检查前，不保证当前机器可用。

## 10. 下一步小样本验证

### 10.1 固定试验

- 地区：洛杉矶，明确行政边界或近似范围。
- 五个固定关键词：clothing wholesaler、apparel wholesaler、garment importer、apparel trading company、clothing retailer，附地区上下文。
- 第一轮最多 20 家去重企业，可靠后扩大至 100 家。
- Maps 并发 1，设总时间限制，外部付费调用为 0。
- 人工基线：同条件查询的可见条目，仅比较同条件样本，不称为地区总体。

### 10.2 必须测量

| 指标 | 定义 |
|---|---|
| 可追溯率 | 有查询、来源定位和时间的企业／所有自动发现企业 |
| 地区与类型正确率 | 人工审核符合条件的企业／审核企业 |
| 重复率 | 确认重复但未处理记录／审核记录 |
| 稳定性 | 正常完成、部分完成、阻塞和失败分别统计 |
| 官网正确率 | 确属企业的官网／审核的已关联官网 |
| 采购入口发现率 | 有明确人员／部门／申请入口的企业／完成补全企业 |
| 个人采购邮箱发现率 | 有证据明确对应个人采购邮箱的企业／完成补全企业 |
| 未完成率 | 失败或阻塞企业／计划补全企业 |
| 成本 | 运行、审核耗时、峰值资源及付费调用次数 |

必须测一次中断恢复及一次旧资料重新复核。复核必须重新观察旧页面，不能用跳过旧记录的续跑选项替代。

通过追溯、停止、错误识别及样本审核后再集成。没有测试数据前，不承诺每天抓取量、稳定成功率和采购邮箱覆盖率。

## 11. 对原方案的修订

- 新增 gosom 项目作为 M0 优先验证候选，不直接从零开发所有 Maps 交互。
- 保持 Python、FastAPI、SQLite 主架构。
- Playwright 保留为可控的自建适配器及动态官网工具。
- 官网首选 HTTPX；其他爬虫框架按实测需求再引入。
- 免费运行成为明确约束，不再作为预算待确认项。
- 区分续跑、发现新增、旧资料复核。
- 本轮只调研和修订文档，没有安装或运行爬虫。
